    r2xsql is a radare2 core plugin and nothing else
    
    Collapses r2xsql from three artifacts and two servers down to one artifact: the
    core plugin. Net -1255 lines, and two dependencies gone.
    
    WHAT IT IS NOW
    
    The plugin registers three command forms and owns nothing else:
    
        sql  <SQL>                 a radare2 table, for a human at the console
        sql,<tablequery> <SQL>     the same table, shaped by an r2 table query
        sqlj <SQL>                 the JSON envelope, for a program
    
    Because these are ordinary r2 commands, every transport radare2 already has
    carries them: the console, r2pipe, `=h`, and MCP. That is the whole point --
    there is no r2xsql server, no r2xsql port, and no second binary.
    
    WHAT WAS REMOVED, AND WHY
    
      * The CLI. `radare2 -q -A -c '"sqlj SELECT ..."' file` is the batch tool, and
        it arrives without a second binary to build, ship, version and document.
      * The MCP server. r2's own MCP reaches the same command dispatch, so `sqlj`
        is already an MCP tool with nothing for us to maintain.
      * The HTTP server (and cpp-httplib with it). r2's `=h` already serves
        POST /cmd/, in-process, against the same RCore.
      * The r2xsql_type_define() scalar function. A full C declaration is what
        radare2's `td` is for, and `td` reaches the session over the same transport
        as the SQL, so the function was a second door onto one room. `types` keeps
        INSERT for an empty struct/union/enum shell, and DELETE.
    
    `regexp()` is the one remaining non-stock SQL function, and it stays for a
    reason that distinguishes it from the above: SQLite reserves the REGEXP
    operator syntax but ships no implementation, so `WHERE name REGEXP '...'` is a
    runtime error unless the host registers it. No r2 command expresses that.
    
    FORMATTING IS RADARE2'S
    
    `sql` renders through r_core_table_new + r_table_tostring rather than a
    hand-rolled writer, so it honours cfg.table.format, cfg.table.maxcol,
    cfg.table.wrap and scr.utf8 like every other command, and inherits any format
    r2 grows later. `sql,<tablequery>` feeds r_table_query, which is where :csv,
    :tsv, :json, :html, :r2, :quiet and paging come from -- none of it implemented
    here.
    
    The table query is a SUFFIX, before the SQL, ending at the first space. That is
    forced rather than chosen: the query language reserves ',' and '/', and SQL is
    full of both, so a trailing query could not be told apart from the statement.
    `is,` and `iz,` solve it the same way and this follows them.
    
    `sqlj` deliberately does NOT go through the table API. r_table_tojson emits
    only pj_kn/pj_ks -- there is no pj_knull -- and skips any cell whose text is
    empty, so
    
        sql,:json SELECT NULL AS a, '' AS b, 'x' AS d   ->  [{"d":"x"}]
        sqlj      SELECT NULL AS a, '' AS b, 'x' AS d   ->  rows: [[null,"","x"]]
    
    `a` and `b` vanish rather than arriving as null or empty, indistinguishable
    from a column that was never selected. The envelope also carries per-statement
    errors, multi-statement results and timings, which a table has nowhere to put.
    
    HELP AND DISCOVERY
    
    `sql?` goes through RCoreHelpMessage and r_core_cmd_help, so it renders like
    any other command's help. `sql,?` reaches the table-query language's own help
    -- routed through r_cons on purpose, because r_table_query prints its help with
    eprintf, which over `=h` means HTTP 200 and an empty body.
    
    The `sql.` namespace is subcommands and never SQL; a dotted statement is
    refused with a message rather than executed. `sql.tables` and `sql.views`
    answer by querying sqlite_master rather than printing a literal list, so they
    cannot drift from the schema -- the hardcoded catalog they replace had drifted
    to naming 33 tables and 8 views while the build exposed 47 and 13.
    
    TESTS
    
    The shipped suite is now r2r, radare2's own runner: 22 cases under
    tests/db/extras/cmd/, replacing the pytest suite. Run with
    
        make -C tests R2XSQL_PLUGIN_DIR=<build>/bin
    
    Two notes for anyone extending it. Tests must sit under an `extras` path
    component or r2r runs radare2 with -NN and R2_NOPLUGINS and the plugin's
    command does not exist; R2_LIBR_PLUGINS in r2r's environment is then the only
    way to point at an uninstalled build. And because r2r compares stdout
    byte-for-byte with no normalisation, assertions go INTO the SQL --
    `SELECT count(*) > 0 FROM funcs` with EXPECT pinned to 1 -- which stays correct
    across compilers, architectures and r2 versions where a raw count would not.
    
    KNOWN ISSUE, NOT INTRODUCED HERE
    
    r2r hangs on Windows before running anything. It reproduces against radare2's
    own test/db, so it is not specific to these tests; CI builds on Windows but
    only runs r2r on Linux and macOS. This suite is verified on Linux.

-## Command-Line Interface
+## Running r2xsql
+
+r2xsql is a radare2 **core plugin** — `core_r2xsql` — and nothing else. There is
+no `r2xsql` binary, no r2xsql server and no r2xsql port. It registers two
+commands inside radare2:
+
+| Command | Output |
+|---|---|
+| `sql <SQL>` | a radare2 table (for a human at the console) |
+| `sql,<tablequery> <SQL>` | the same table, shaped by r2's table query |
+| `sqlj <SQL>` | the JSON envelope (for a program) |
+
+Discovery follows r2's `?` conventions: `sql?` for the command, `sql,?` for the
+table-query language, `sql.?` for subcommands. `sql.tables` and `sql.views`
+list the real surface (they query `sqlite_master`, so they cannot go stale);
+you can get the same thing as data with
+`sqlj SELECT name, type FROM sqlite_master ORDER BY type, name`.
+**`sql.` is a subcommand namespace and never carries SQL** — `sql.SELECT 1` is
+refused, not executed.
+
+`sql` renders through radare2's own table API, so it honours `cfg.table.format`
+and `scr.utf8` like `afl,` or `iz,`. The `sql,` form feeds `r_table_query`,
+which supplies `:csv`, `:tsv`, `:json`, `:html`, `:r2`, `:quiet` and paging.
+The table query is a **suffix ending at the first space**, so it can never
+collide with the statement: `sql,:csv SELECT name, size FROM funcs`.
+**You are a program: use `sqlj`, not `sql,:json`** — see below for why.
+
+Because these are ordinary r2 commands, every transport radare2 already has
+carries them: the console, r2pipe, r2's HTTP server (`=h`), and MCP. That is
+the design — r2xsql does not need a transport of its own.
+
+`sqlj` is not just `sql` with different formatting, and **`sql,:json` is not a
+substitute for it.** It runs through `run_script`, so it executes **multiple
+statements** (one result object each), and it distinguishes **SQL NULL from the
+empty string**.
+
+A radare2 table can do neither. Its JSON serializer emits only numbers and
+strings — there is no `null` — and it drops any cell whose text is empty:
+
+```
+sql,:json SELECT NULL AS a, '' AS b, 'x' AS d   ->  [{"d":"x"}]
+sqlj      SELECT NULL AS a, '' AS b, 'x' AS d   ->  rows: [[null,"","x"]]
+```
+
+`a` and `b` do not return as null or empty — they vanish, indistinguishable
+from a column you never selected. Use `sqlj` for anything programmatic.
+
+### RULE 1: wrap the command in double quotes
+
+**Unwrapped queries fail silently — HTTP 200, empty body, no error anywhere.**
+
+radare2's command parser claims characters SQL uses constantly, *before* the
+plugin runs:
+
+- any command containing `>` returns an **empty result** unless it starts with
+  `"` (r2 reads it as "redirect output to a file");
+- any command containing `|` is piped **to the shell** under the same
+  exemption, with r2's sandbox switched off for that command.
+
+```bash
+# WRONG - returns nothing, and writes a file named `100`
+sqlj SELECT name FROM funcs WHERE size > 100
+# WRONG - `||` is SQL string concat; this reaches your shell
+sqlj SELECT a || b FROM t
+
+# RIGHT - wrap the whole command; the closing quote must be last
+"sqlj SELECT name FROM funcs WHERE size > 100"
+```
+
+The `'…'` single-quote form is a **trap, not an alternative**: it bypasses the
+rest of r2's parser so it works at the console, but both guards above test for
+`"` specifically, so over HTTP it still returns an empty body. `~` and `@`
+inside SQL `'…'` literals are already safe; `>` and `|` are not.

+R2R  ?= r2r

+	@mkdir -p build
+	$(CC) -O0 -g -o $@ fixture.c
+
+test: $(FIXTURE)
+	$(R2R_ENV) $(R2R) -u -L -C . db/extras/cmd
+
+clean:
+	rm -rf build

+R2_LIBR_PLUGINS=/path/to/build/bin r2r -u -L -C . db/extras/cmd
+```
+
+The plugin is ABI-locked to the radare2 it was built against
+(`R2_ABIVERSION`), so these must be the matching pair — a mismatch shows up as
+radare2 refusing to load the plugin.
+
+## Layout
+
+```
+db/extras/cmd/core      core tables over a real compiled binary
+db/extras/cmd/schema    views and sqlite_master introspection
+db/extras/cmd/types     the type system (td defines, SQL reads)
+db/extras/cmd/write     the writable surface and its injection guard
+db/extras/cmd/format    the sql / sql, / sqlj output forms
+```
+
+**Why `db/extras/`.** r2r runs radare2 with `-NN` and `R2_NOPLUGINS` unless a
+test's path contains an `extras` component — and with no plugins there is no
+`sql` command to test. `extras` directories are also skipped during plain
+recursion, which is why the path is named explicitly above. Each test passes
+`ARGS=-N` so a developer's `.radare2rc` cannot change the result.
+
+**Why the assertions look the way they do.** r2r compares stdout
+byte-for-byte with no normalisation, so "more than zero functions" cannot be
+written as an `EXPECT`. Instead the assertion goes *into* the SQL — `SELECT
+count(*) > 0 FROM funcs` — and `EXPECT` pins the literal `1`. That stays
+correct across compilers, architectures and radare2 versions, which a raw
+count would not.
+
+## Known issue: r2r on Windows
+
+`r2r` hangs on Windows before running anything, including against radare2's
+own `test/db`. It is not exercised by upstream CI there. These tests are
+therefore verified on Linux; the suite itself is platform-neutral.
